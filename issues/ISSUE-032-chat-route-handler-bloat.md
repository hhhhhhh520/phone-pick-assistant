# ISSUE-032 chat.py 路由处理器臃肿（120 行业务编排逻辑）

> 创建时间: 2026-06-25
> 状态: 🔴 未解决
> 优先级: P2（架构问题，不影响功能，但影响维护）

## 问题描述

`backend/api/routes/chat.py` 的 `generate()` 异步生成器（105-226 行）包含全部业务编排逻辑：

1. 发送 session ID（107）
2. 发送 intent 信息（110）
3. 判断是否需要追问（116-120）
4. 追问分支：生成问题、发送、保存（122-134）
5. 对比分支：检索手机、发送、流式对比、保存（136-154）
6. 推荐分支：检索、流式推荐、cons 后处理、型号解析、过滤、发送、保存（156-224）
7. 发送 done 事件（226）

一个路由处理器做了太多事情，违反单一职责原则。

## 出现原因

MVP 阶段快速实现，功能逐步叠加。每次新需求（多轮对话 `84d8b62`、型号匹配 `7c846d1`、推荐优化 `8e77403`）都在 `generate()` 里加代码，没有重构。

## 解决方案

**方案**: 抽取 `ChatOrchestrator` 服务，路由层只处理 HTTP 关注点。

```
chat.py (路由层)          ChatOrchestrator (服务层)
├─ 验证输入               ├─ 意图识别
├─ 创建/获取 session      ├─ 需求画像管理
├─ 返回 StreamingResponse  ├─ 追问/推荐/对比编排
└─ 错误处理               ├─ cons 后处理
                          ├─ 型号解析与过滤
                          └─ session 消息保存
```

**注意**: 这是一个较大的重构，建议在功能稳定后再做。当前优先级为 P2。

## 影响面

- 功能影响：重构后功能不变
- 测试影响：需要为 `ChatOrchestrator` 补充单元测试
- 风险等级：中（重构涉及核心流程，需要充分测试）

## 验证方法

1. 全量 E2E 测试：推荐、对比、筛选、多轮对话
2. 为 `ChatOrchestrator` 编写独立单元测试
3. 确认 SSE 事件流格式不变

## 相关文件

- `backend/api/routes/chat.py` — 重构目标
- 新建 `backend/services/chat_orchestrator.py` — 编排逻辑
